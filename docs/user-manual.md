# User manual

This manual is for users of a repository derived from `assetpack-template`.

The repository generates image assets from structured GitHub Issues. A valid request is validated, converted into a fixed prompt recipe, generated by the configured image model, and committed under `assets/generated/`.

## 1. What you can do

Use this repository when you want a repeatable image-generation record stored in Git:

```text
GitHub Issue
  -> validation
  -> policy check
  -> image generation
  -> committed PNG and metadata
  -> Issue comment
```

Generated records are stored under:

```text
assets/generated/issue-<issue-number>/<recipe_id>/
```

A generated record normally contains:

```text
image.png
prompt.txt
negative_prompt.txt
request.json
metadata.json
report.json
README.md
```

## 2. Before you submit a request

Confirm that the repository maintainer has completed these setup steps:

1. GitHub Actions are enabled.
2. The request label exists. The default label is `asset-request`.
3. The Issue template named `Asset request` is available.
4. The workflow has permission to write repository contents and Issue comments.
5. At least one smoke request has already succeeded.

If these are not true, the request may validate correctly but fail before a committed asset is produced.

## 3. Submit an asset request

1. Open a new GitHub Issue.
2. Select the `Asset request` Issue template.
3. Fill in the structured fields.
4. Keep text fields ASCII-only unless the repository policy has been changed.
5. Select a model.
6. Select a license.
7. Submit the Issue with the `asset-request` label.

Default fields are:

| Field | Required | Example | Notes |
| --- | --- | --- | --- |
| Subject | yes | `sleeping cat` | Main object or character. |
| Scene | yes | `simple sitting pose` | Visual setting or pose. |
| Audience | yes | `children` | Intended audience or usage context. |
| Constraints | no | `simple shapes, no background clutter` | Additional structured constraints. |
| Model | yes | `default` | Use `default` unless you need a configured alternate. |
| License | yes | `CC0-1.0` | Must match one of the allowed license values. |

Example request:

```text
Subject: sleeping fox
Scene: sitting on a white rug
Audience: children
Constraints: simple composition, friendly pose
Model: default
License: CC0-1.0
```

## 4. Model choices

The default template currently allows:

| Option | Meaning |
| --- | --- |
| `default` | Use the repository default model. |
| `sdxl-turbo-quality` | Default image-generation model. |
| `ssd-1b-lcm-lora-quality` | Alternate image-generation model. |

Use `default` for normal requests. Select a named model only when the repository maintainer has told you to compare or override model behavior.

## 5. What happens after submission

The workflow runs when the Issue is opened, edited, reopened, or labeled.

Expected success sequence:

1. The Issue is parsed into structured request fields.
2. The request is validated against `assetpack.yml`.
3. A deterministic recipe id is computed.
4. If the recipe already exists, the workflow comments with the existing asset path.
5. If the recipe is new, the workflow generates an image.
6. The workflow commits the generated record under `assets/generated/`.
7. The workflow comments on the Issue with the result.

## 6. Read the generated result

Open the directory shown in the success comment.

Use these files:

| File | Purpose |
| --- | --- |
| `image.png` | Generated image. |
| `prompt.txt` | Final prompt used for generation. |
| `negative_prompt.txt` | Negative prompt, when configured. |
| `request.json` | Normalized request fields from the Issue. |
| `metadata.json` | Model id, size, recipe id, hashes, and generation metadata. |
| `report.json` | Generation status and diagnostic details. |
| `README.md` | Human-readable summary for the generated asset. |

The generated asset index is:

```text
assets/generated/README.md
```

## 7. Duplicate requests

The same structured request resolves to the same `recipe_id`.

If that asset already exists, the workflow should not generate a second image. It should comment with the existing path instead.

To intentionally generate a different asset, change one of the structured fields.

## 8. Common validation failures

| Failure | What to do |
| --- | --- |
| Missing required field | Edit the Issue and fill the missing field. |
| Invalid license | Choose one of the allowed license values. |
| Invalid model id | Use `default` or a listed model option. |
| URL in a structured field | Remove URLs from request fields. |
| Unknown non-empty section | Use only the Issue template fields. |
| Non-ASCII text | Rewrite checked fields using ASCII-only text. |
| Missing required term | Adjust the structured fields so the final recipe includes the required term. |

After editing the Issue, re-run by editing, reopening, or re-applying the configured request label.

## 9. Generation or commit failure

If validation passes but no asset is committed:

1. Open the failed workflow run from the Issue or Actions tab.
2. Check the generation step logs.
3. Check uploaded artifacts for `request.json` and `report.json`.
4. If the failure looks transient, re-run the workflow.
5. If the failure repeats, ask the maintainer to inspect model download, timeout, dependency, runner resource, and repository permission settings.

## 10. Maintainer checklist before public use

Before accepting external requests, maintainers should verify:

- `assetpack.yml` matches the repository theme and allowed content policy.
- The `asset-request` label exists.
- GitHub Actions are enabled.
- Workflow permissions allow commits and Issue comments.
- The default model can run on the configured runner.
- One smoke Issue has successfully produced a committed asset.
- Duplicate request behavior points to the existing asset.
- `assets/generated/README.md` is updated after generation.

## 11. Rules for external users

- Submit only structured requests through the Issue template.
- Do not edit generated asset records manually.
- Do not request content outside the repository policy.
- Use the Issue comment as the source of truth for success or failure.
- Treat committed generated records as durable build artifacts.
